# Hypercube Office 0.2.0: audit follow-up

Follow-up to [the 0.2.0 audit](v0.2.0-audit.md), written on 2026-10-09 after the owner answered
its questions. It covers the mouse-wheel zoom lag the owner reported, scrolling in very long
PDFs, what the 21 interface languages really cost, and a full account of when the app uses the
network. Every number was measured unless it says otherwise; the measuring machine is the same
4-core Linux virtual machine as in the audit, so ratios matter more than absolute times.

## 2. Step 1 in plain words

Step 1 is one to two weeks of small, low-risk changes:

1. **A warning before editing a digitally signed PDF**, offering to save the changes as a copy so
   the signed original stays valid.
2. **Faster opening of large PDFs**: stop re-reading the whole file a second time on every open
   (measured: first page of a 2,100-page file in 4.6 s instead of 8.5 s).
3. **A smaller installer**: drop about 26 MB of unused or duplicated files.
4. **Remove GenOffice leftovers** and refresh two libraries with published security fixes.
5. **Fix one unreliable automated test.**
6. **Make README and PRIVACY agree** on network use, and close the two network gaps in section 5.
7. **New: smoother wheel zoom and scrolling** (section 3).

## 3. Why wheel zoom and scrolling lag, and a measured fix

### What happens on each mouse-wheel notch today

1. **The zoom step is uneven.** A Windows mouse notch sends a scroll amount of about 100, and the
   viewer subtracts `0.006 × 100` from the zoom (`apps/pdf/src/renderer/App.tsx`, wheel handler).
   That is +60% per notch at 100%, but only +15% at 400%, so zoom feels jumpy near 100% and slow
   when already zoomed in.
2. **Every notch redraws every visible page from scratch**, immediately, at full sharpness
   (`apps/pdf/src/renderer/PdfPage.tsx`). Turning the wheel quickly starts and cancels several
   full redraws in a row.
3. **Every notch re-renders the whole viewer**, a single 9,400-line component with a box for
   every page of the document, then moves the scroll position to keep the spot under the cursor
   still, which forces the browser to lay out all of those boxes at once. In a CPU profile of
   zooming the 2,100-page file, the browser's own layout and painting took about half of the
   time, and the scroll-anchoring step was the single largest app function.
4. **Finding which page you are on gets slower the further you are into the book.** On every
   scroll event the viewer re-adds the heights of all pages above you, once per page
   (`handleScroll` → `rowTop`, quadratic in the page number). A faithful copy of that code costs
   8 ms per scroll event at 10% of a 2,100-page book, 33 ms halfway and 87 ms near the end, before
   any drawing, against a budget of about 16 ms per frame.

### The trial fix

[`prototypes/wheel-zoom-and-scroll.patch`](prototypes/wheel-zoom-and-scroll.patch) (77 added
lines in three files, not applied to the app):

- each notch zooms by the same ratio (×1.2) at any zoom level;
- on a zoom step the existing page images are stretched to the new size in the same frame as the
  page boxes, and the sharp redraw waits until the wheel has been still for 150 ms;
- the text layer (used to select and copy text) is resized instead of rebuilt;
- the current page is found with a running total instead of the quadratic loop.

It passes the PDF viewer's unit tests (726 of 727; the one failure also fails without the patch
and is specific to Linux fonts) and the end-to-end tests for fit-to-width, text selection, links,
form fields, bookmarks, find and redaction.

### Measured effect

Real app, 3 alternating runs per build, medians. "Freeze" is the longest stretch without a new
frame on screen; "stutter" is the total time the screen was blocked by long tasks during the
gesture; "sharp again" is the time from the last notch until every visible page is redrawn.

| Document and gesture                       | Measure                        |    Today | Trial fix |
| ------------------------------------------ | ------------------------------ | -------: | --------: |
| 14 pages, fast spin (6 notches in and out) | Longest freeze                 |   117 ms |     33 ms |
|                                            | Stutter                        |   248 ms |      0 ms |
| 700 pages, fast spin in the middle         | Longest freeze                 | 1,033 ms |     83 ms |
|                                            | Stutter                        |    3.2 s |    0.27 s |
|                                            | Sharp again                    |    2.9 s |    0.17 s |
| 2,100 pages, fast spin in the middle       | Longest freeze                 |   950 ms |    167 ms |
|                                            | Stutter                        |    2.7 s |    0.86 s |
|                                            | Sharp again                    |    2.0 s |    0.46 s |
| 2,100 pages, single notches                | Delay before the screen reacts |   214 ms |     26 ms |
|                                            | Stutter                        |    3.2 s |     1.3 s |
| 2,100 pages, scrolling at 90% of the book  | Stutter                        |    1.4 s |    0.37 s |
|                                            | Typical frame gap (95th pct.)  |   233 ms |    100 ms |

**Trade-off:** after a single notch the page now looks slightly soft for about 0.2 s before the
sharp version appears (on the 14-page file, "sharp again" went from 51 ms to 260 ms). The wait
can be shortened, or skipped for an isolated notch, when this becomes the real change.

**What is left:** on the 2,100-page book each notch still blocks for about 150 ms, because the
viewer keeps a box for every page in the window and lays them all out on each zoom step. The fix
for that is to keep only the pages near the screen (with one spacer standing in for the rest),
which is the long-document item in step 2. It also cuts memory and the per-scroll work for
very long books.

**Method note.** An earlier attempt at this comparison was invalid: the build swap between runs
silently failed, so both arms used the same build. The numbers above come from a re-run in which
the active build was checked before every round.

## 4. Do the 21 interface languages slow the app down?

**A little, not a lot.** Every editor currently loads the text of all 21 languages when it
opens, although only one is shown.

How much of each built editor is translation text for languages other than English and Arabic:

| Part of the app       | Built size | Without the 19 other languages | Saved         |
| --------------------- | ---------: | -----------------------------: | ------------- |
| Slides editor         |    4.17 MB |                        2.95 MB | 1.22 MB (29%) |
| Home screen and tabs  |    1.01 MB |                        0.82 MB | 0.18 MB (18%) |
| Docs editor           |   10.62 MB |                        9.26 MB | 1.36 MB (13%) |
| Sheets editor         |   30.21 MB |                       28.26 MB | 1.95 MB (6%)  |
| PDF viewer and editor |    4.37 MB |                        4.17 MB | 0.20 MB (5%)  |
| Whole app (all parts) |   88.06 MB |                       82.26 MB | 5.79 MB (7%)  |

Measured in the real app, 3 alternating runs each, median time from launch until the document is
visible, and memory:

| Opening        | All 21 languages | English + Arabic only | Memory saved (all processes) |
| -------------- | ---------------: | --------------------: | ---------------------------: |
| Sheets (.xlsx) |            3.1 s |                 2.8 s |                       ~17 MB |
| Slides (.pptx) |            2.2 s |                 1.9 s |                        ~7 MB |
| PDF            |            2.2 s |                 2.1 s |                        ~0 MB |
| Docs (.docx)   |            2.4 s |                 2.3 s |                        ~7 MB |
| Home screen    |            1.0 s |                 1.0 s |                        ~0 MB |

On a slower 4 GB laptop the time saved will be larger, roughly 0.3 to 1 second per Sheets or
Slides tab (an estimate: the cost is parsing code, which scales with processor speed).

**Recommendation:** do not delete the languages. Load only the language in use, on demand. That
gives nearly the same saving and keeps every language available. It is a mechanical change to
the string tables (medium effort), and it should come after the PDF speed fixes, which matter
far more.

## 5. When does the app use the network?

The app has no telemetry, no accounts and no background uploads. The PDF, Word, Excel and
PowerPoint editors and the Markdown editor block all web content. A live test (every connection
attempt traced while opening one file of each type) confirmed that opening PDF, Word, Excel,
PowerPoint and Markdown files makes no web requests.

These are all the ways the app can reach the internet:

| #   | What you do                                                            | What the app contacts                                          | What leaves your computer                                                                                               | Automatic?                                             |
| --- | ---------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1   | **Start the app** (nothing else)                                       | `redirector.gvt1.com` (Google's spell-check dictionary server) | Your computer's internet address and the dictionary requested                                                           | **Yes, every start (seen on Linux; check on Windows)** |
| 2   | **Open an HTML file** that refers to web images, fonts or scripts      | Every website the file refers to                               | Your internet address, the time, and whatever the addresses carry (tracking pixels often carry a document or person ID) | **Yes, on opening**                                    |
| 3   | Paste content copied from a web page into Docs                         | The websites hosting its images                                | Your internet address and the image addresses                                                                           | On paste                                               |
| 4   | Export a Markdown note with web images to Word                         | The image websites                                             | Same                                                                                                                    | On export                                              |
| 5   | Crop or cut out a web image in the HTML editor                         | That image's website                                           | Same                                                                                                                    | On that action                                         |
| 6   | "Save image as…" on a web image (only possible in the HTML preview)    | That image's website                                           | Same                                                                                                                    | On that action                                         |
| 7   | Settings > About > "Check now", or the daily check if you turned it on | `api.github.com`                                               | Your internet address and the app's request for the latest version                                                      | Off by default                                         |
| 8   | "Download and install" an update                                       | `github.com`                                                   | Same                                                                                                                    | Only when clicked                                      |
| 9   | Click a link in a document                                             | Nothing: your web browser opens the link                       | —                                                                                                                       | —                                                      |

No document content is ever sent. The risk in rows 1-6 is that the website owner (or Google in
row 1) learns your internet address and the moment you did something, and in row 2 a tracking
pixel can tell the sender that you opened their HTML file.

Not network use, checked: the Zotero integration talks only to the Zotero program on the same
computer (`127.0.0.1`); the downloadable-fonts feature in Slides has no server configured and
never runs; links open in your browser, not inside the app.

### The two new findings

**HTML files load web content the moment they are opened.** The HTML editor's preview has no
content policy of its own and allows scripts (`apps/html/src/main/preview-protocol.ts`,
`apps/html/src/renderer/preview/PreviewFrame.tsx`). In the live test, opening a small HTML file
fetched a Google Fonts stylesheet, a script, an image and a 1-pixel tracking image whose address
carried an identifier, without any click. `PRIVACY.md` mentions this; `README.md` says the app
never connects. Suggested fix: block web content in the preview by default and show a bar
("This document refers to content on the internet. Load it?"), the way email programs do.

**A spell-check dictionary request at every start.** Each launch in the test, even with no
document open, tried to reach `redirector.gvt1.com`, the server Chromium uses to download
spell-check dictionaries. On Windows, Electron normally uses the built-in Windows spell checker,
so this may not happen there; it must be checked on the laptop (for example with Windows
Resource Monitor's Network tab right after starting the app). The fix is one line in the main
process, `session.setSpellCheckerDictionaryDownloadURL()` pointing at a local folder (or
bundling the English and Arabic dictionaries), so no build can ever fetch one.

### Options for the user-triggered downloads (rows 3-6)

| Option                       | What you keep                                                   | What you lose                                                    |
| ---------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| Keep as is, document clearly | Pasting from the web keeps pictures                             | A website can see your internet address when you paste or export |
| Ask first (recommended)      | Same, after one click: "Download 3 pictures from the internet?" | One extra click                                                  |
| Remove                       | Strictly offline                                                | Pictures pasted from web pages arrive as empty boxes             |
